# تقرير مراجعة DevOps و CI/CD (P10)
**المرحلة:** P10 — Release Engineering Review  
**التاريخ:** 2026-07-03  
**النطاق:** `render.yaml`، `vercel.json`، `Dockerfile`، `.github/workflows/`، نصوص `package.json`  

---

## 1. عدم اتساق بيئات النشر (Render مقابل Vercel)
**الخطورة:** High  
**الملف/الموقع:** `render.yaml` و `vercel.json` و `.github/workflows/deploy-demo.yml`  
**المشكلة:** يوجد تضارب جوهري في إعدادات النشر. إعدادات `render.yaml` تهيئ التطبيق كخدمة Node.js متكاملة (Full-stack) تعتمد على `server.js` لمعالجة الواجهة والـ API معاً. بينما إعدادات `vercel.json` (والتي يتم استخدامها فعلياً في سير عمل GitHub Actions `deploy-demo.yml`) تعتمد على Vite وتوجه مسارات `/api/(.*)` إلى مسار وهمي `/api/index.ts` غير موجود أصلاً في المشروع.  
**الأثر المحتمل:** إذا كان Vercel هو بيئة الإنتاج الفعلية (كما يوحي GitHub Actions)، فإن كل نقاط النهاية (API Endpoints) الموجودة في الباكيند (`server.js`) معطلة تماماً ولن تعمل، مما يكسر وظائف حيوية مثل معالجة الذكاء الاصطناعي.  
**التوصية المقترحة:** تحديد بيئة النشر الأساسية وإزالة ملفات الإعداد للبيئات الأخرى لتجنب التشتت. إذا كان Vercel هو الهدف، يجب تحويل `server.js` إلى Vercel Serverless Functions بدلاً من تطبيق Express.

## 2. تشغيل حاوية Docker بصلاحيات الـ Root
**الخطورة:** Medium  
**الملف/الموقع:** `Dockerfile`  
**المشكلة:** ملف الـ Dockerfile مبني على `node:20-alpine` ولكنه لا يحدد مستخدم غير جذري (non-root user). الحاوية ستعمل بصلاحيات `root` بشكل افتراضي.  
**الأثر المحتمل:** في حال وجود ثغرة في التطبيق تسمح بتنفيذ أوامر عن بعد (RCE)، سيتمكن المهاجم من التحكم في الحاوية بصلاحيات الـ root، مما يسهل الهروب من الحاوية (Container Breakout) في بعض البيئات.  
**التوصية المقترحة:** إضافة `USER node` قبل أمر `CMD`، وتغيير ملكية الملفات المناسبة باستخدام `COPY --chown=node:node`.

## 3. تجاهل الباكيند والاختبارات في خط أنابيب CI
**الخطورة:** Medium  
**الملف/الموقع:** `.github/workflows/ci.yml` و `.github/workflows/deploy-demo.yml`  
**المشكلة:** سير العمل الخاص بالـ CI يقوم بتشغيل `npm run lint` و `npm run build` فقط. الأمر `npm run build` يقوم ببناء الواجهة الأمامية (Vite) ويتجاهل بناء الباكيند (`build:server`). الأهم من ذلك، لا يتم تشغيل الاختبارات (`npm test`) على الإطلاق عند رفع الكود.  
**الأثر المحتمل:** يمكن دمج كود يحتوي على أخطاء برمجية في الباكيند أو يفشل في اجتياز اختبارات الوحدة دون أن يكتشف خط الأنابيب (CI) ذلك.  
**التوصية المقترحة:** إضافة خطوة `npm run test` لتشغيل الاختبارات كشرط أساسي لنجاح الـ CI، وتعديل خطوة البناء لتشغيل `npm run build:all` للتأكد من نجاح بناء الباكيند والواجهة معاً.

## 4. غياب استراتيجية التراجع (Rollback Strategy)
**الخطورة:** Medium  
**الملف/الموقع:** إعدادات النشر ومستندات المشروع  
**المشكلة:** لا يوجد أي أثر لاستراتيجية تراجع برمجية منظمة. بينما توفر منصات مثل Render أو Vercel زر للتراجع، لا توجد نصوص أو آليات للتعامل مع عمليات التراجع المرتبطة بقاعدة البيانات (مثل التراجع عن تعديلات تمت على المخطط Schema أثناء إصدار فاشل).  
**الأثر المحتمل:** في حال نشر تحديث يحتوي على تغييرات في قاعدة البيانات ثم الحاجة للتراجع للكود القديم، قد يتعارض الكود القديم مع مخطط قاعدة البيانات الجديد، مما يؤدي إلى توقف النظام بالكامل.  
**التوصية المقترحة:** دمج أداة لإدارة هجرات قاعدة البيانات (مثل Prisma، Drizzle، أو نصوص هجرة مخصصة) تتضمن آليات "Down Migrations" وتوثيق إجراءات التراجع بوضوح.

## 5. أمان نصوص البيانات التجريبية (Demo Seed/Reset)
**الخطورة:** Low  
**الملف/الموقع:** `scripts/demo-seed.ts` و `scripts/demo-reset.ts`  
**المشكلة:** النصوص تعتمد على ملف `.env` لقراءة `VITE_SUPABASE_URL` والمفتاح. على الرغم من أنها مقيدة بتعديل وحذف البيانات التي تحمل المعرف `demo-tenant` فقط، إلا أنه في حال تنفيذها بالخطأ في بيئة الإنتاج أو من جهاز مطور يحمل مفاتيح الإنتاج، فإنها ستتصل وتعدل في قاعدة البيانات الحقيقية. بالإضافة إلى ذلك، هي تعتمد على `ANON_KEY` مما قد يفشل إذا كانت سياسات RLS تحظر الحذف بدون تسجيل دخول.  
**الأثر المحتمل:** مخاطرة منخفضة لحذف بيانات حقيقية، لكن الممارسة غير آمنة وقد تولّد أخطاء غير متوقعة بسبب RLS.  
**التوصية المقترحة:** إضافة تأكيد إضافي (Prompt) يطلب من المستخدم تأكيد العملية إذا كان الرابط يشير لبيئة الإنتاج، أو منع تشغيل هذه النصوص تماماً إذا كان `NODE_ENV === 'production'`.
