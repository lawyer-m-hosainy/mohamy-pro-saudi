# تقرير مراجعة واجهات برمجة التطبيقات (API Design Review)
**المرحلة:** P4
**النطاق:** `server.js` - جميع الـ Endpoints، طبقة Middleware، معالجة الأخطاء

## الملاحظات المكتشفة

[الخطورة: Critical] | [server.js] | اختلاف جوهري في البنية التحتية (Drift) عن التصميم المعماري: الكود يستخدم Firebase Admin (Firestore & Auth) بدلاً من Supabase (PostgreSQL + RLS) كما هو موصوف في وثيقة المنصة. | تعارض كامل مع التصميم المعماري الموثق، ويعني أن المنصة الحالية لا تعتمد على Supabase أو سياسات RLS، مما يؤدي إلى انهيار استراتيجية العزل (Tenant Isolation) المخطط لها والاعتماد على الكود البرمجي بالكامل للعزل. | الترحيل الفوري من Firebase إلى Supabase وتفعيل سياسات RLS، وتحديث `server.js` لاستخدام عميل قاعدة البيانات المتوافق.

[الخطورة: High] | [server.js - Endpoints] | غياب تام لمعظم واجهات برمجة التطبيقات (API) الخلفية للوظائف الرئيسية للنظام (Finance, Trust Accounting, Team, Analytics... الخ). الملف يحتوي فقط على واجهات لـ الذكاء الاصطناعي وإدارة مبدئية لـ Cases. | الاعتماد المباشر على الواجهة الأمامية للتواصل مع قاعدة البيانات بدون طبقة خلفية للتحقق يزيد من تعقيد الأمان ويعرض المنطق التجاري والاختصاصات القانونية لتلاعب المستخدمين. | بناء مسارات خلفية مخصصة (Backend Routes) للعمليات الحساسة في جميع الأقسام وعدم الاعتماد الكلي على الواجهة الأمامية أو الوصول المباشر للبيانات.

[الخطورة: High] | [server.js - SPA Fallback] | مسار SPA Fallback (`app.get('*')`) يغطي جميع مسارات الـ API غير الموجودة. عند طلب مسار API غير متوفر (مثل `GET /api/cases`) يتم إرجاع ملف `index.html` بدلاً من رمز الخطأ 404. | التطبيقات المستهلكة للـ API ستتلقى كود HTML بدلاً من خطأ بصيغة JSON، مما يؤدي إلى أخطاء غير متوقعة (JSON Parse Error) وانهيار التطبيقات المتعاملة معها. | إضافة Middleware خاص بمسارات `/api/*` لإرجاع 404 JSON لأي مسار واجهة برمجية غير موجود، قبل استدعاء مسار `app.get('*')`.

[الخطورة: Medium] | [server.js - Error Handling] | عدم تناسق بنية الاستجابة للأخطاء. يتم إرجاع `{ error: "message" }` بشكل مخصص، وفي حالة أخطاء الذكاء الاصطناعي (Catch blocks) يتم إرجاع حالة HTTP `200` مع رد وهمي (Mock Response) متجاهلاً الخطأ الفعلي. | إخفاء الأخطاء الحقيقية للذكاء الاصطناعي يصعب تتبع المشاكل (Debugging)، كما أن غياب بنية قياسية للخطأ يعقد المعالجة في الواجهة الأمامية. | توحيد شكل الاستجابة ليكون قياسياً (مثل `{ code, message, details }`)، وإرجاع أكواد HTTP صحيحة لأخطاء الذكاء الاصطناعي.

[الخطورة: Medium] | [server.js - HTTP Status Codes] | استخدام رموز حالة HTTP بشكل غير دقيق: يتم إرجاع `403` عند فشل التحقق من `idToken` (بدلاً من `401`)، ويتم استخدام `400` لأخطاء التحقق من المدخلات بدلاً من `422`. | عدم التوافق مع معايير REST API القياسية مما يسبب ارتباكاً لمطوري الواجهات أو التكامل المستقبلي. | استخدام `401` للمصادقة الفاشلة/منتهية الصلاحية، و`403` لرفض الصلاحيات المحددة، و`422` لبيانات الطلب غير الصالحة.

[الخطورة: Medium] | [server.js - API Versioning] | غياب تام لاستراتيجية تعيين الإصدارات (Versioning) للمسارات (جميعها تبدأ بـ `/api/` مباشرة دون إشارة للإصدار). | صعوبة شديدة في إجراء أي تغييرات لاحقة أو إطلاق ميزات جديدة مع الحفاظ على التوافق مع الإصدارات السابقة (Backward Compatibility) للعملاء. | إضافة مسار الإصدار لجميع الواجهات الحالية (مثال: `/api/v1/ai`) واعتماد استراتيجية إصدارات واضحة في تصميم الواجهات البرمجية.

[الخطورة: Low] | [server.js - Rate Limiting] | محدد الطلبات (Rate Limiter) الخاص بالذكاء الاصطناعي `aiRateLimiter` يعتمد على عنوان الـ IP فقط بدلاً من ربطه بمعرف المكتب (`tenantId`). | قد يؤدي إلى حظر مكاتب كاملة إذا كان مستخدموها يشاركون نفس الـ IP الداخلي، أو استهلاك مفرط للموارد إذا تم تغيير الـ IP. | استخدام دالة `keyGenerator` داخل إعدادات مكتبة `express-rate-limit` لربط الحد الأقصى للطلبات بمعرف `req.tenantId` بدلاً من الـ IP.

## إجابات نقاط التحقق (Checklist Status)
- **Point 1 (Endpoints Check):** يوجد واجهات مصغرة فقط للـ AI والـ Cases. بقية الأقسام (Finance, Trust Accounting, Analytics, الخ) غير موجودة إطلاقًا في طبقة الخادم المرفقة (تم تسجيلها كمشكلة High).
- **Point 2 (Error Consistency):** غير متناسقة وتفتقر لهيكلة قياسية، تعتمد على استجابة `{ error }` أو نصوص افتراضية بحالة 200 (تم تسجيلها كمشكلة Medium).
- **Point 3 (Status Codes):** أخطاء في استخدام رمز 401 مقابل 403، وغياب 422 (تم تسجيلها كمشكلة Medium).
- **Point 4 (AI Length Limits):** **تم التحقق بنجاح**. حدود 5000/10000/50000 مطبقة ومفروضة من جهة الخادم (Server-side) داخل الـ Middleware المسمى `aiSecurityMiddleware`.
- **Point 5 (Tenant Scoping in logic):** واجهات الـ Cases الموجودة تتحقق برمجياً من الـ `tenantId`، لكن نظراً لاستخدام `admin.firestore()` فإن الخادم يتجاوز كل سياسات الأمان الذاتية لقاعدة البيانات ويستخدم Service Role Key فعلياً (مندرجة تحت مشكلة الـ Drift الحرجة).
- **Point 6 (Versioning):** لا يوجد أي استراتيجية للإصدارات (تم تسجيلها كمشكلة Medium).
- **Point 7 (SPA Fallback Security):** توجد ثغرة حيث أن مسار `index.html` يعالج مسارات API المفقودة بدلاً من إرجاع خطأ 404 برمجي (تم تسجيلها كمشكلة High).

## OUT OF SCOPE — FLAG FOR LATER
- استخراج صلاحيات المستخدم (`req.userRole`) يتم دعمه عبر `req.headers['x-user-role']` وهو ما قد يمثل ثغرة لتزوير الصلاحيات إذا لم يكن هناك طبقة API Gateway تحذف هذه الترويسات من الطلبات الخارجية.
